# Checkout codes: the shared contract (#402)

The one place the wallet, the code store (`imani-checkout-codes`), the PHP core
(`imani-coupon-core`) and gateway-customer agree on bytes. Each of them tests
against `vectors.json` next to this file. The issue (#402) gives the reasons, and this
file only fixes the wire format.

## 1. The code

| Property | Value |
| --- | --- |
| Alphabet | Crockford base32: `0123456789ABCDEFGHJKMNPQRSTVWXYZ` (no I, L, O, U) |
| Body | 12 symbols: 11 random data symbols (55 bits) + 1 check symbol |
| Check symbol | Luhn mod 32 over the 11 data symbols (see below) |
| Display form | `IMANI-XXXX-XXXX-XXXX` |
| Compact form | `IMANIXXXXXXXXXXXX` (17 characters). Used where hyphens are not allowed (Shopify gift cards: 8-20 alphanumerics) |
| Generated by | the code store, from a CSPRNG, retrying on a collision |

55 bits rather than 60: the display grouping has 12 body symbols and one of
them is the check. R0 makes a guess worth nothing on PHP platforms, and the
lookup is authenticated and rate limited (R2, R3), so 55 bits is ample.

### Luhn mod 32

`value(c)` is the index of `c` in the alphabet.

```
check(data):                      # data = 11 symbols
  factor = 2, sum = 0
  for c in reversed(data):
    a = factor * value(c)
    sum += a // 32 + a % 32
    factor = 3 - factor           # 2,1,2,1,...
  return alphabet[(32 - sum % 32) % 32]

valid(body):                      # body = 12 symbols, check last
  factor = 1, sum = 0
  for c in reversed(body):
    a = factor * value(c)
    sum += a // 32 + a % 32
    factor = 3 - factor
  return sum % 32 == 0
```

It catches every single-symbol typo and most adjacent swaps, locally, before
any network call.

### Normalising what a person typed

In this order:

1. Uppercase (ASCII only).
2. Delete spaces, tabs, `-`, `_`, `.`.
3. The result must start with `IMANI`. Strip it. (The prefix is matched
   **before** step 4, because `IMANI` contains an `I`.)
4. In the body, map `O`→`0`, `I`→`1`, `L`→`1`. Any other symbol outside the
   alphabet (including `U`) makes the input **not a code**.
5. The body must be exactly 12 symbols and pass `valid`.

The result is the **canonical code**: the compact form, `IMANI` + body.
Anything that fails steps 3-5 is "not an Imani code". Platforms leave it alone
so ordinary coupons keep working. Failing the check symbol alone is a typo,
reported as *"Check the code: a character looks wrong."*

### What the store keeps

The store never keeps the code. It keeps
`code_hash = hex(sha256(utf8(canonical code)))`, and looks up by it. A dump of
the database names no code. Logs show at most `code_hash[0..12]`.

## 2. A part

One coupon locked to the shop key `S`. A coupon is carried by **1..k proofs** (the gateway signs
one locked successor per power-of-two output, as for Cashlinks), and every proof of a part has
the same secret shape:

```
P2PK_VOUCHER(data = 02‖S, locktime = x, refund = [02‖R], sigflag = SIG_ALL, n_sigs = 1,
             voucher_id, <the coupon's terms>, max_sats)
```

This is exactly `linkLockProposal`'s shape (`src/lib/cashlinkLock.ts`), signed
by the same gateway route (`POST /api/v1/wallet/vouchers/cashlink/lock`), with
`S` in place of the link key. Rules:

- `R ≠ S`. `R` is per part and derived (`imani-checkout-refund/v1/` label, a wallet-wide
  counter), never the customer's identity key. All proofs of one part share one `R`.
- Every part of one code has the **same** `x`, the same `unit`, and the same
  `issuer` tag (the stall's x-only key). The voucher signature is the **gateway's**
  (`issuer_pubkey`, gateway-customer's identity key), never the stall's.
- `assertNotOpenAfterLocktime` holds for every proof.
- A part travels as one `cashuB` token holding all its proofs, all with the same `voucher_id`,
  `S`, `x` and `R`. Its amount is the credited face value of the sum of its proofs
  (`creditableFaceValue`). Every proof gets its own pre-signed refund at the relay.

## 3. The code store API

Base path `/v1/checkout-codes`. All calls are NIP-98 (kind 27235, `u` = the
full URL, `method`, and `payload` = sha256 of the body for POSTs). Amounts are
integers in the unit's **minor units**. Times are epoch **seconds**.

### `POST /v1/checkout-codes`: deposit (customer)

```json
{
  "idempotency_key": "uuid",
  "stall_pubkey": "x-only hex",
  "shop_key": "x-only hex (S)",
  "unit": "eur",
  "amount": 2500,
  "expires_at": 1767000000,
  "parts": [ { "token": "cashuB…", "amount": 1000 }, { "token": "cashuB…", "amount": 1500 } ]
}
```

- The NIP-98 caller is the customer. Change and returns are locked to it.
- `amount` must equal the sum of the parts' `amount`, and each part's `amount`
  must equal its credited face value (`creditableFaceValue`).
- 1 ≤ parts ≤ 20.
- Verification is all-or-nothing (R8). One bad part refuses the deposit, with
  `refusal` naming the first problem and `part` its index.

`201 {"code": "IMANI-…", "status": "reserved", "expires_at": …}`. The same
`idempotency_key` from the same caller replays the same answer.

Refusals (`422 {"refusal": NAME, "part": i}`): `MALFORMED`, `TOO_MANY_PARTS`,
`AMOUNT_MISMATCH`, `UNIT_MISMATCH`, `NOT_AUTHENTIC`, `WRONG_ISSUER`,
`WRONG_LOCK_KEY`, `NOT_A_LOCK` (shape), `LOCKTIME_WITHOUT_REFUND`,
`MIXED_EXPIRY`, `EXPIRY_OUT_OF_WINDOW`, `ALREADY_SPENT` (NUT-07),
`DUPLICATE_PART`. `409 MINT_UNAVAILABLE` is retryable.

### `GET /v1/checkout-codes/{code}`: look up (shop)

The NIP-98 caller must be the code's `S`. `{code}` is any typed form. The store
normalises it.

`200`:
```json
{ "status": "reserved|held|redeemed|cancelling|cancelled|expired",
  "amount": 2500, "unit": "eur", "expires_at": 1767000000, "stall_pubkey": "…",
  "held_by": "order ref, only when held by this caller",
  "parts": [ { "amount": 1000, "splittable": false, "min_step": 1 }, … ] }
```

An unknown code, a code for another `S`, and a malformed code all get the
**same** `404 {"refusal":"NOT_FOUND"}`, byte for byte (R2).

### `POST /v1/checkout-codes/{code}/hold`, `/release`, `/redeem` (shop)

Body `{"order_ref": "string ≤ 128"}`.

- `hold`: `reserved → held`, with a TTL (default 30 min, refreshed by a repeat
  hold from the same `order_ref`). Holding again with the same `order_ref` is
  idempotent. A different `order_ref` gets `409 HELD`.
- `release`: `held → reserved`, for the holding `order_ref` only. Otherwise it
  is a no-op `200`.
- `redeem`: `held → redeemed`, for the holding `order_ref` only. Returns
  `{"parts":[{"token":"cashuB…","amount":…}], "customer_pubkey":"…"}`. A replay
  with the same `order_ref` returns the same body (R4).
- On any other state these return `409 {"refusal": "<STATE>"}`.

### `POST /v1/checkout-codes/{code}/cancel` (customer, the depositor only)

`reserved → cancelling`. `409 HELD` while held.

### `POST /v1/checkout-codes/{code}/cancelled` (shop)

Body `{"tokens":["cashuB…"]}`: the parts, swapped back and locked to the customer.
`cancelling → cancelled`, and the tokens go to the outbox for the customer.

### `POST /v1/checkout-codes/{code}/change` (shop, after redeem)

Body `{"tokens":["cashuB…"]}`: change and unneeded parts locked to the
customer. They go to the outbox.

### `GET /v1/checkout-codes/mine` (customer)

The caller's codes, newest first:
`[{ "code", "status", "amount", "unit", "expires_at", "shop_key", "stall_pubkey" }]`.
This is the only place the store returns a code, and only to its depositor. The
store therefore keeps the code **encrypted** for the depositor too: AES-GCM under a
server key, beside `code_hash`.

### `GET /v1/checkout-codes/exposure?shop_key={S}` (stall)

R5: what a shop key could redirect if it were stolen, for the stall's Terminals page
("3 codes, €45.00 outstanding at shop.example"). The NIP-98 caller must be the
`stall_pubkey` the codes were deposited for. `200 {"codes": n, "amount": minor, "unit": "eur"}`
over codes locked to `S` for this stall in `reserved`, `held` or `cancelling`; one unit per
stall (ADR 0005). It returns no code and no customer. Any other caller, or an `S` this stall
has no codes for, gets `{"codes": 0, "amount": 0, "unit": <stall unit>}`, so the answer
reveals nothing about other stalls. The wallet shows no figure for anything but a well-formed
200 (`shopExposure.ts`).

### State machine

```
reserved ──hold──▶ held ──redeem──▶ redeemed
   │  ▲              │
   │  └──release / TTL┘
   ├──cancel──▶ cancelling ──cancelled──▶ cancelled
   └── now ≥ expires_at (also from cancelling and held) ──▶ expired
```

Every transition is one conditional `UPDATE … WHERE status = ?`, so exactly one
writer wins.

## 4. The stall's profile field

On the stall's kind-30078 `imani:merchant` record (ADR 0012):

```json
"online_shop": { "url": "https://shop.example", "redeem_key": "<S x-only hex>",
                 "platform": "woocommerce|wordpress|magento|shopify", "since": 1767000000 }
```

The wallet takes `S` only from here (R7). It is absent, malformed, or not
64-hex: no online shop.

The stall publishes it while the shop's redeem-only terminal row is in service, and
republishes without it when the terminal is revoked (`onlineShopProfile.ts`). One per stall.

### Enrolling the shop

The plugin generates `S` at setup and shows the owner

```
imani-shop-enrol:1:<S hex>:<url>:<platform>:<created_at>:<sig>
```

where `created_at` and `sig` are the terminal enrolment proof (`terminalEnrolProof.ts`):
BIP-340 by `S` over `sha256("imani-terminal-enrolment" US "1" US S US created_at)`, valid
for 24 hours. The url (https) may contain colons and is what lies between `S` and the
platform. The stall's wallet sends `1:<created_at>:<sig>` as `X-Imani-Terminal-Enrolment`
with a `redeem-only` credential mint locked to `S`, exactly as for a till, and the plugin
then receives its credential by NIP-17 like a till (`terminalDelivery`'s setup code and
`enrolled` notice). The url and platform are not signed by `S`; the owner confirms them on
screen and the stall signs them into §4.

## 5. Settling: how value leaves `S` (redeem, change, cancel)

A swap cannot change who a coupon is locked to: the gateway's voucher signature covers `data`.
So, as for Cashlinks, the holder of `S` **burns** each proof and the gateway **re-signs**
successors, one burn buying one set of signatures. The new gateway route makes the shop's power
exactly "pay the stall, or give it back to the customer", and nothing else.

### `POST /api/v1/wallet/vouchers/checkout/settle` (gateway-customer, the shop)

NIP-98 by any key (the authority is `authorization`). Body:

```json
{ "predecessor_secret": "…", "proposed_secrets": ["…"], "authorization": "sig by S",
  "predecessor_proof": { "amount", "id", "C", "dleq" }, "burn_outputs": [ … ] }
```

Signed only when every rule holds:

1. The predecessor is the §2 shape (LinkLock), issued by this gateway, not a credential.
   Note: before `x`, `S` can already move a part anywhere with the generic re-sign route (it is the
   holder). This route exists because that route keeps `locktime`/`refund`, so a successor sent to
   the stall would still be refundable by the customer after `x`. Restricting `K` here is defence
   in depth, not the boundary: the boundary is R5 (a shop key is a revocable terminal, exposure
   bounded by its outstanding codes).
2. `authorization` is BIP-340 by `S` (the predecessor's `data`) over
   `sha256("imani/voucher-checkout-settle/v1" ‖ predecessor ‖ each proposal)`, length-prefixed
   the same way as `cashlinkDigest`.
3. The mint reports the predecessor SPENT, and `SpendingPathway` says by `S` (before `x`). A
   refund-pathway spend is the customer's, and is never settled.
4. 1 ≤ proposals ≤ 20. Each proposal is `P2PK_VOUCHER(data = 02‖K, n_sigs = 1)` with **no**
   `locktime`, **no** `refund`, `sigflag` absent (SIG_INPUTS), a fresh distinct nonce, the
   predecessor's terms unchanged (`VoucherTerms`, with `locktime`/`refund`/`sigflag` removed from
   the comparison) and a canonical `max_sats`, where `K` is **either** the `issuer` tag (the
   stall) **or** the predecessor's refund key `R` (the customer). Any other `K` is refused.
5. `Σ max_sats ≤` the burn's proven amount (`SuccessorSatBound`). One burn, one claim (the shared
   claim ledger), and an identical resend replays.

Refusals reuse the Cashlink route's names where they apply, plus `LOCK_KEY_NOT_ALLOWED` (rule 4)
and `NOT_THE_SHOP_PATHWAY` (rule 3).

Each successor carries one power-of-two output, so the shop sends one proposal per output of the
amount it re-locks (for example 200 sats to the stall = 128 + 64 + 8, three proposals).

### `POST /api/v1/wallet/vouchers/checkout/unlock` (gateway-customer, the customer)

It turns a returned coupon locked to `R` back into an ordinary, unlocked one:

1. The predecessor is `P2PK_VOUCHER(data = 02‖K)` with no locktime and no refund, issued here,
   and not a credential (licence or terminal: `isCredential`, as the split and re-sign routes).
2. `authorization` is by `K` over `sha256("imani/voucher-checkout-unlock/v1" ‖ …)`.
3. The mint reports it SPENT, and only `K` could have spent it.
4. The proposal is the unlocked `VOUCHER` with the same terms (as `cashlink/resign` builds it),
   and `max_sats ≤` the burn.
5. The NIP-98 caller is not the coupon's issuer (customer-to-customer, as for Cashlinks).

### What the shop does at redeem (`imani-coupon-core` `Redeemer`)

For every proof of every part, all derived from `S` and the proof (as `cashlinkLock.ts` derives
from `R`), so a crash anywhere resumes:

1. **Burn:** swap the proof (SIG_ALL witness by `S`) into plain outputs whose blinding factors are
   derived from `S` (`imani-checkout-burn/v1/`). NUT-09 restore recovers a lost answer.
2. **Settle:** propose successors: the applied share locked to the stall, any change locked to
   `R`. Parts the order does not need at all go back whole, locked to `R`.
3. **Carry:** swap the burnt plain proofs into the signed successors (derived blinding, single
   power-of-two output each).
4. **Deliver:** stall-locked tokens to the stall by NIP-17 (one token per `voucher_id`, ADR 0011).
   `R`-locked tokens to the store (`/change` after redeem, `/cancelled` after cancel), which gives
   them to the customer. Neither the shop nor the store can spend either kind.

Cancel is the same with every successor locked to `R`.

## 6. Notifications to the customer

The store sends them itself, as NIP-17 gift wraps from its own key to the depositor's key:

```json
{ "type": "imani-checkout-code/1", "event": "redeemed|expired|cancelled|change",
  "code_hash": "…", "amount": 800, "unit": "eur", "tokens": ["cashuB…"] }
```

`tokens` (R-locked) appear only on `change` and `cancelled`. `redeemed` carries the amount spent.
