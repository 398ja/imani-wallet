# #410: a gift as a checkout code for the stall's online shop

Status: design and scoped plan. The gifting page ships the choice behind `VITE_GIFTING_CODE_GIFTS=on`
(off by default). The backend below is not built yet.

## When the choice appears

Only when the stall's public `imani:merchant` record carries a well-formed `online_shop`
(checkout-codes contract §4, parsed fail-closed by `parseOnlineShop`). The stall publishes that field
only while the shop's redeem-only terminal is in service, so it is the real signal that the shop takes
codes at checkout. No field, a malformed field, or the build switch off: no choice, a voucher as today.

## What the page sends

The draft request gains one optional field, `"gift": "code"`. Absent means a voucher, so every
existing request, draft and Stripe session is unchanged. The page refuses a draft whose answer does not
echo the same kind (`draftMatches`), so a payment-adapter that does not know the field (and pins a
voucher) can never be paid as a code. Delivery is always `{kind: "email", email, refundPubkey, sealed}`.

## What has to be built (end to end)

1. **payment-adapter (Purchase Draft API #305)**: accept `gift: "code"` only for a stall whose record has
   a valid `online_shop`; pin `shop_key` (S) and the shop url on the draft (new columns
   `gift_kind`, `shop_key`, migration); echo `gift` in the draft JSON; carry it on the debt the webhook
   hands purchase-issuer. Refuse with a clear 409 if the shop field went away between draft and pay.
2. **purchase-issuer**: after Stripe, mint the vouchers as today but lock each to `S` (not to `L`), with
   locktime `x` and refund to the gift's refund key, exactly the part shape of contract §2; deposit them
   at `imani-checkout-codes` `POST /v1/checkout-codes` with an idempotency key of `<draftId>:code`;
   arm the pre-signed refunds at the relay. Then mail the recipient the code (new mailer template
   `gift-code`: amount, shop url, `IMANI-XXXX-XXXX-XXXX`, expiry, "check the balance" link to
   `/v1/code-check/{code}`), idempotency `<draftId>:code-mail`. Scrub the seal (no claim link is needed).
3. **imani-checkout-codes**: the depositor (NIP-98 caller) is the issuer, not a person. Needed: change and
   `rebalanced` notices for issuer-deposited codes must reach the buyer's refund key instead of the
   issuer, or the issuer forwards them (decision below). No change to codes, parts, or the shop API.
4. **imani-mailer**: the `gift-code` template, and the buyer's notices (code used, code expired and the
   rest returned to you).

## Open decisions (need the owner)

- **Who is `R` for a gifted code?** Contract §2 wants `R` derived per part and never an identity key. For
  a guest buyer, the gift's refund key (their return link) fits. For a signed-in buyer the refund key is
  their wallet key today, which the contract forbids for parts. The issuer cannot derive `R` (it never
  holds the refund secret), so the proposal is that the page makes a fresh `R` for every code gift,
  signed-in buyers included, and sends it home by the return link. This changes G3.
- **Can the buyer take back an unused code?** Codes are bearer instruments (#472: `cancel` refused). The
  rest comes back at `x` only. The review copy already says "whatever isn't spent by <expiry> comes back
  to you"; confirm that is the promise.
- **Who gets change notices** (point 3).

## Scoped plan

1. payment-adapter: field, pinning, migration, tests (1 PR).
2. imani-checkout-codes: notice routing for issuer deposits (1 PR, small).
3. purchase-issuer + imani-mailer: locked-to-S mint, deposit, code email (1 PR, the bulk).
4. Turn on `VITE_GIFTING_CODE_GIFTS` on staging; run the gifting e2e with a real Woo shop.
