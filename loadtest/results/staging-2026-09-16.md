# Staging performance run — 2026-09-16

Re-run of the performance suites against **staging** (`wallet.staging.398ja.xyz`),
from an L1 laptop over WAN. Method follows `loadtest/README.md`: verify the
signer, smoke, then ramp.

- wallet SHA `fe1e57f` (0.3.2)
- staging host: 4 cores, 7.7 GiB RAM, 60% disk, load ~1.4 at rest
- k6 v2.0.0, signer sidecar 12 workers

## TL;DR

The device-side suite is **healthy and unchanged** (cold boot 111ms against a
109ms baseline). The gateway-side suite is **largely unrunnable against
staging**, and the reasons are findings in their own right rather than harness
faults:

| Scenario | Result | Why |
|---|---|---|
| signer-check | **PASS** | 7149 sigs, 0 invalid, 356/s, p99 207ms (checker-bound) |
| smoke | **PASS** | 9/9 checks, gateway avg 717ms over WAN |
| drain ramp | **RAN, degraded** | 241 drains vs **2083 rate-limited** |
| issuance ramp | **BLOCKED** | portal needs a session cookie; NIP-98 cannot get one |
| send ramp | **BLOCKED** | depends on issuance |
| browser cold boot | **PASS** | 111ms, no regression |
| browser populated rung | **BLOCKED** | unlock needs a gateway that answers `/api/v1/auth/*` |

Nothing here suggests the *service* is slow. Where it was allowed to work it
was quick and correct: 482/482 checks passed, zero failures, p95 321ms
including a transatlantic round trip. What the run found instead is that
**staging's protections are keyed in a way that makes the deployment
un-load-testable**, and one of those protections is silently degrading under
load in a way that matters beyond testing.

## Finding 1 — the rate limit is IP-keyed, so one client is one budget

**The dominant effect in the whole run.** 2083 of 2324 drain iterations (90%)
came back 429 from the edge.

`gateway-core`'s `application.yml` sets a blanket
`security.rate-limit.requests-per-minute: 100`, counted per caller address.
`address-keyed` names only `/api/v1/nip05` and `/api/v1/accounts/register` for
*per-address* path limits, but the global 100/min already applies per address
to everything else. A load generator is one address, so the entire 21-VU pool
shared a single 100/min budget regardless of the 21 distinct pubkeys signing.

Measured throughput was therefore **not** a capacity result:

    drains        241        succeeded, all empty
    rate limited  2083
    gateway_ms    med 202  p95 321  max 4786
    signing_ms    med 3    p95 5          (the generator is not the constraint)

This is working as designed for a *hostile* caller. It is wrong for two real
populations:

1. **Load tests.** Any run from one host measures the limiter, not the service.
2. **Customers behind shared egress.** `trusted-proxy-count=2` is set on
   staging and the XFF chain chains correctly, so ordinary users do get
   distinct buckets — but a corporate NAT, a campus, a carrier CGNAT or a VPN
   exit collapses to one. 100 requests/min across every customer behind one
   address is a low ceiling for a wallet whose receive page polls.

Evidence that this is not hypothetical: during the ramp the edge log shows a
**real Firefox session** on `/receive` taking 429s alongside the test traffic.

    "POST /api/v1/incoming-notifications/drain HTTP/1.1" 429 ... Firefox/155.0
    "POST /api/v1/payment-receipts/drain HTTP/1.1" 429 ... Firefox/155.0

A browser that was not part of the test was collateral damage of the test.
That is the finding: the two are indistinguishable to the limiter.

**Recommended:** key the limit on the authenticated pubkey wherever a request
carries a valid NIP-98 signature, and keep the address key only for the
unauthenticated paths that mint identity (`/nip05`, `/accounts/register`),
which is exactly what `address-keyed` already documents as its purpose. A
signed request has a better identity available than its source address, and
using it removes both the NAT problem and the load-test problem at once. The
drain path in particular is a poll on the customer's own queue.

## Finding 2 — the NIP-98 replay cache overflows under load

Present the whole run, and it is a **correctness** issue, not a speed one:

    nip98_eventid_cache_overflowing evictions=2659 max_size=10000 ttl_seconds=120
      effect=event_ids_forgotten_while_still_replayable
      action=raise_max_size_to_at_least_peak_req_per_sec_times_ttl

    nip98_eventid_ttl_shorter_than_requested requested_seconds=600 actual_seconds=120
      effect=replay_window_between_the_two

452 overflow reports and 2573 TTL warnings in twenty minutes. The cache does
its own arithmetic and tells you the answer: at `max_size=10000` and a 120s
TTL it can only remember 83 requests/second before it starts forgetting IDs
that are still inside their replay window.

Two distinct problems, both already named by the log line:

- **Capacity.** `DEFAULT_MAX_SIZE` is not sized from the peak request rate.
- **Window mismatch.** Something asks for a 600s memory and gets 120s, leaving
  a 480s gap in which a captured request can be replayed.

Worth noting this fired at a *rate-limited* 19 req/s. The cache is counting
requests the limiter rejected, which means the two protections interact: the
replay cache is doing its most work precisely when it is least able to.

The class also warns `nip98_eventid_cache_is_process_local`, so this does not
survive a restart and is not shared across replicas.

**Recommended:** size `max_size` from measured peak × TTL with headroom, and
reconcile the 600s request against the 120s actual so the window is whatever
was intended rather than the smaller of two numbers nobody chose.

## Finding 3 — issuance and send cannot be measured against staging at all

Both ramps died in `setup()` after the full 60s timeout, having proved nothing.

The cause is structural, not a bug. `loadtest/lib/gateway.js` plays the edge
by sending `X-Edge-Auth` + `X-Auth-Permissions: coupon:issue`, which is what a
local stack needs. Staging's nginx runs `nap_auth.lua` in front of
`/api/v1/portal/`, and that gate **deliberately clears any client-supplied
`X-Auth-Pubkey` / `X-Auth-Permissions` / `X-Edge-Auth`**, validates a session
cookie against gateway-core, and re-injects the values from the validate
response. Confirmed by hand:

    POST /api/v1/portal/vouchers                  401 {"message":"No session cookie"}
    ... with X-Edge-Auth + X-Auth-Permissions     401

That gate is correct and should stay: it is the only thing between a customer
and `coupon:issue`. But it means **no NIP-98-only client can issue on
staging**, so issuance — which the README calls both the first measurement and
the tool that funds everything after it — has no path here.

The 60s failure mode is worth fixing regardless. `setup()` retries the probe
three times to wait out a saturated rate-limit window, which is right when the
cause is throttling and pure cost when the cause is a 401. A 401 is not a
rate limit and will not become one by waiting.

**Recommended:** fail fast and name the cause when the probe returns 401 with
no session cookie, rather than retrying for a minute. Then either give the
suite a way to obtain a session (a NAP login in `setup()`), or record in the
README that issuance and send are local-stack scenarios, as ADR 0003/0004
already do for redemption and splitting.

## Finding 4 — drain measures an empty queue, so the number is a floor

The suite says this itself, loudly, and it held again here: 241 drains, 241
empty, 0 envelopes. What was measured is the cost of answering "nothing
waiting" — endpoint, signature check, queue poll — not the work of returning
and acknowledging envelopes.

Meanwhile `payment-receipts.q` on staging is **not** empty. During the run
gateway-core was consuming receipts timestamped `Jul 05` and `Jul 21` — two
months stale. Whatever produced them, nothing drained them at the time. That
is a backlog worth a look on its own, and it is also the population the drain
scenario needs: pointing the scenario at customers who actually have
envelopes waiting would turn its floor into a real measurement.

## Finding 5 — smaller things worth recording

- **gateway-core runs at 63% of a 1 GiB cap at idle** (646 MiB), the tightest
  headroom of any container on the host. No OOM and no restarts, so this is a
  watch item rather than a defect, but it is the container most likely to be
  the first casualty of a real load event. `imani-mint-rest` (54% of 768 MiB)
  and `gateway-portal` (53% of 768 MiB) are next.
- **The wallet ships a 1.06 MB main chunk** (340 KB gzipped) and Vite warns
  about it every build. Cold boot is 111ms on a laptop over localhost, so this
  is invisible here and would not be on a phone over mobile data. The browser
  suite cannot see it because it measures a local `dist/`.
- **`loadtest/signer-check.mjs` needs `undici`, which is not a dependency.**
  It fails `ERR_MODULE_NOT_FOUND` on a clean checkout; installed by hand for
  this run. One line in `package.json`.
- **The default `GATEWAY_URL` is `customer.staging.398ja.xyz`, which no longer
  exists** — it is explicitly 404'd as a retired host in
  `imani-deploy/nginx/conf.d/imani.conf`. Every tier now answers on
  `wallet.staging.398ja.xyz`. A run that forgets to set the variable fails
  against a host that was retired rather than against staging.

## What this run did not establish

No capacity figure for staging. The limiter bounded every scenario long before
any subsystem did, so "where does staging break first" is still unanswered —
except that the answer is currently "at its own rate limiter, at 100
requests/minute per address". Until Finding 1 is addressed, that will be the
answer to every gateway-side run from a single host, and the real ceiling
stays invisible behind it.
