# RCA: paid-unissued quotes (cashu-mint#469)

Traced 2026-09-24 against the staging mint database and service logs.

## The finding in one line

**The mint is abandoning its own saga.** A quote is created, an invoice is
raised, the customer pays it, the mint **accepts** the payment, and then the
request that started the whole thing fails on a *later* step and returns an
error to the client. Nobody ever comes back to mint, because from the client's
point of view the call failed.

The money is taken. The voucher does not exist. Nothing retries.

## Not the zero-amount bug

Checked first, because the two incidents overlap in time. **None of the 12
stranded quotes has `amount = 0`:**

| amount | count |
|---|---|
| 1 sat | 5 |
| 2 sat | 1 |
| 21 sat | 2 |
| 300 sat | 2 |
| 8388608 sat | 2 |

And none is a voucher quote at all: every one is a plain `mint_quote` with no
matching `voucher_quote` row. So `cashu-mint#468` is a different failure on the
same weekend, not this.

## What the gauge counts

```sql
SELECT count(*) FROM mint_quote q
 WHERE q.lifecycle_state = 'PAID'
   AND q.updated_at < :updatedAtBefore   -- default PT1H
```

A quote that was paid and never advanced past `PAID`. The repository comment is
explicit that no reconciler can fix this, because issuing needs the client's
blinded outputs, which the mint never persists.

## The sequence, from the logs

Taking `8aa24e04-b11d-4c69-8d62-4a1566af5ba8` (1 sat, stranded 22:04:52):

Zero `MintTask` entries for that quote id. The payment was accepted and the

**Why it never returned** is in `gateway-customer`, on the request that created

22:04:59.297  CashuWalletMintApi  Failed to request voucher mint quote: ... faceValue=1

The caller received a 500 and stopped. It had no reason to poll a quote whose
creation it believes failed.

## Why the mint returned 90008

On the mint side, in the same second:

```
22:04:59.264  Sending HTTP request: POST http://phoenixd-mock:9740/createinvoice
22:04:59.271  Received response: status=200   {"amountSat":0,...}
22:04:59.287  PhoenixdGateway  Created mint quote: quoteId=e1b8f435-...
22:04:59.291  SQL Error: 0, SQLState: 23514
22:04:59.291  ERROR: new row for relation "voucher_quote" violates check
              constraint "voucher_quote_charged_amount_positive_chk"
22:04:59.292  VoucherMintQuoteTask  voucher_quote persist_failed quote_id=e1b8f435-...
22:04:59.293  CashuController  cashu_error code=90008 {"error":"voucher_quote_persist_failed"}
```

So the database **does** carry the invariant this system needed:

```sql
CHECK ((charged_amount > 0))
```

**It is enforced in the wrong order.** The sequence in `VoucherMintQuoteTask` is:

1. compute the price (zero, for a 1-sat voucher at 10%)
2. **create the gateway invoice** (irreversible, and immediately payable)
3. persist `voucher_quote` (rejected by the constraint)
4. throw

Step 2 has already happened when step 3 fails. The invoice exists, phoenixd will
honour it, and the webhook that settles it arrives at a mint that has thrown the
request away.

## The two defects, stated separately

**1. A saga step that is irreversible runs before its validation.**

The constraint is correct and the ordering defeats it. Anything that creates an
external, payable artefact must not do so until every local precondition has
passed. `persistVoucherQuote` already fails closed on purpose, and its comment says
*"the client MUST NOT receive a quote_id that can't be redeemed"*, but by then
the invoice is out.

`cashu-mint@12da540f` fixes the *trigger* by flooring the fee so the price is
never zero, and by refusing the quote before the gateway is called. That closes
this instance. **It does not close the ordering.** Any other persist failure at
step 3 (a transient DB error, a future constraint) strands a paid invoice the
same way.

**2. An accepted payment with no issuance has no owner.**

Once the request has returned 500, nothing in the system is responsible for
that money. The gauge sees it; no process acts on it. That is by design for the
issuance half, since the mint cannot mint without the client's blinded outputs,
but "cannot auto-issue" is not the same as "cannot do anything":

- the client could be told the quote id even on failure, so a retry can resume
- a paid-unissued quote could be refundable after a TTL
- at minimum it could be surfaced per-quote rather than as a bare count

## Every stranded quote fits the same shape

All 12 have an `accepted` webhook event and no issuance:

| quote | amount | paid at | note |
|---|---|---|---|
| `1d5ccbf2` | 8388608 | 09-22 11:39 | accepted, never issued |
| `1ef2279d` | 8388608 | 09-22 13:03 | accepted, never issued |
| `87a2b5fa` | 300 | 09-22 16:02 | **created 08-29**, paid 24 days later |
| `ec7bc224` | 21 | 09-23 19:39 | |
| `284ac38b` | 21 | 09-23 19:39 | |
| `8aa24e04` | 1 | 09-23 22:04 | traced above |
| 4 x `1 sat` | 1 | 09-24 00:03 | same probe run |
| `88afcc10` | 300 | 08-29 20:47 | oldest |
| `d6cfaa1b` | 2 | 08-30 23:58 | |

`87a2b5fa` deserves a look on its own: created 08-29, `updated_at` 09-22. An
invoice payable 24 days after issue is either a very long expiry or an expiry
that is not enforced, and either way it means a customer can pay for a quote the
mint has long since stopped expecting.

## Why this was never noticed

`MintQuotePaidUnissued` fires on `> 0`, so it went red at the first unit on
09-21 and has said nothing since. It cannot distinguish "still 2" from "now 12".
The count has **risen every day and never once fallen**, which is the signal
that matters and the one the rule cannot express.

Recommended, and already proposed in `imani-deploy#61`:

```yaml
- alert: PaidUnissuedGrowing
  expr: increase(cashu_mint_quote_paid_unissued[24h]) > 0
  for: 1h
```

## Fixes

1. **Reorder `VoucherMintQuoteTask`**: validate and persist before calling the
   gateway, or make the invoice creation compensatable. This is the actual
   defect; the fee floor removed one way of reaching it.
2. **Decide what a paid-unissued quote is owed.** A refund path, a resumable
   quote id returned on failure, or an explicit policy that the money is held
   pending manual action. Today it is none of these.
3. **Alert on the trend**, not the level.
4. **Check the expiry** that let `87a2b5fa` be paid 24 days after creation.
5. **Clean up the 12** once 1 and 2 are settled.
